1 . Introduction 1.1 Problem Statement & Background Modern embedded telemetry systems require real-time data ingestion coupled with cryptographic verification and encryption. Executing high-bandwidth stream hashing (SHA-256) and block cipher transformations (AES-256 CBC) entirely in software on a 32-bit RISC-V core consumes substantial processor execution cycles, which can cause processing delays and increase CPU load during high-rate data transfers. 1.2 Purpose of the SoC The  Cryptographic Telemetry Gateway SoC  is a custom System-on-Chip designed to offload data movement and cryptographic compute overhead from the VeeR EL2 processor core. By combining a 32-bit open-source  VeeR EL2 RISC-V processor  with an autonomous  DMA controller , a shared  64 KB SRAM frame buffer , and dedicated hardware accelerators for  SHA-256  and  AES-256 , the SoC enables hardware-accelerated telemetry ingestion, integrity hashing, and payload encryption with reduced CPU intervention. 1.3 Key Architectural Objectives Hardware Accelerator Offload:  Execute payload integrity verification (SHA-256) and confidentiality enforcement (AES-256 CBC) on dedicated hardware blocks rather than consuming CPU execution cycles with software cryptographic loops. Autonomous Data Movement:  Employ a DMA controller to manage bulk data transfers between system memory and accelerator endpoints, minimizing core involvement in payload routing. Bus Fabric Separation:  Carry both high-throughput data traffic and peripheral control-plane register configuration over a unified 64-bit AMBA AXI4 crossbar. Peripherals with lightweight register interfaces are accessed via AXI4-Lite slave ports directly from the AXI4 interconnect. Event-Driven Exception Handling:  Route timer, DMA, and cryptographic completion/error  events  directly into the VeeR EL2 core’s Programmable Interrupt Controller (PIC) to notify the processor of hardware events. 2. Control Path and System Coordination The control path defines how the VeeR EL2 core orchestrates system operations across the unified AXI4/AXI4-Lite interconnect architecture. Both high-throughput data movement and peripheral control-plane register configuration are carried over the 64-bit AXI4 interconnect. Peripherals with lightweight register interfaces are connected via AXI4-Lite slave ports. 4.1 System Control Topology Control and configuration transactions originate from the core and are exchanged with peripherals through the control-plane hierarchy. Downward Configuration Flow:  Control flows from the VeeR EL2 Core through its LSU master interface across the 64-bit AMBA AXI4 interconnect directly to the AXI4-Lite slave interfaces of individual peripherals and accelerators (Timer, UART, GPIO, DMA, SHA-256, and AES-256 control registers). Upward Event Flow:  Hardware event notifications flow upward from these endpoints into the Programmable Interrupt Controller (PIC), which drives the VeeR EL2 core's external interrupt vector ( extintsrc_req ). This triggers the execution of the corresponding Interrupt Service Routine (ISR), followed by status register readback, event clearance, and the resumption of the main execution flow. 4.2 Step-by-Step Operational Control Sequences A. General Peripheral and Accelerator Initialization Sequence Step 1:  The VeeR EL2 core issues memory-mapped I/O write requests across the AXI4 interconnect to the AXI4-Lite slave interfaces of peripheral control registers. Step 2:  Firmware programs operating modes, intervals for the system timer, baud rates for the UART, and cryptographic parameters such as AES keys and initialization vectors. Step 3:  Software sets active and enable bits in the respective peripheral control registers to start operation. B. Autonomous DMA Control Sequence Step 1:  Firmware programs the DMA transfer source address, destination address, and size parameters via the DMA controller’s AXI4-Lite control interface. Step 2:  Software writes the start command to the DMA control register. Step 3:  The DMA controller operates independently as an AXI4 master and initiates the programmed data transfers without CPU-driven data movement. Step 4:  Data moves independently between System SRAM and the target hardware endpoint. Step 5:  Upon completion of the programmed transfer or detection of a transfer error, the DMA controller asserts  dma_done_irq  or  dma_err_irq , respectively. Step 6:  The event propagates through the PIC to the VeeR EL2 core. Step 7:  The core executes the DMA service routine to read status flags, clear the interrupt, and release the buffer for the next task. C. Cryptographic Accelerator Control Sequence Step 1:  Firmware configures the cryptographic accelerator and DMA transfer parameters required for the operation, including cryptographic configuration and transfer parameters. Step 2:  Firmware enables or initiates the required cryptographic operation and starts the associated data-transfer operation. Step 3:  The configured hardware performs data movement and cryptographic processing independently of core intervention. Step 4:  Upon finalizing the message digest or block cipher transformation, the block asserts  sha_done_irq  or  aes_done_irq . Step 5:  The PIC routes the completion signal to the VeeR EL2 core. Step 6:  The CPU services the corresponding interrupt, reads the relevant completion and status information and, where required, retrieves the cryptographic result before continuing the processing flow. 5. Data Path 5.1 Data-Path Overview [Ingress Path] External Host ──► Serial Line ──► UART ──► AXI4-Lite ──► VeeR EL2 Core ──► AXI4 ──► System SRAM [Data Movement & Processing] System SRAM ──► AXI4 ──► DMA Controller ──┬──► SHA-256 ──► Digest ──► AXI4-Lite / CPU Readback │ └──► AES-256 CBC ──► Ciphertext ──► System SRAM [Egress Path] System SRAM ──► VeeR EL2 (LSU) ──► AXI4-Lite ──► UART ──► Serial Line ──► External Host The data path consists of two cryptographic processing branches. The SHA-256 branch produces an integrity digest, while the AES-256 CBC branch produces the encrypted payload. The architecture does not assume that the SHA-256 output is directly connected to the AES-256 input unless such a dependency is explicitly defined. The DMA controller performs the required transfers between System SRAM and the respective cryptographic accelerator interfaces. The SHA-256 and AES-256 paths are independent processing branches and are not assumed to operate simultaneously unless explicitly scheduled by the system control flow. 5.2 Data Ingress Ingress Source: The data path begins at the external host, which supplies raw telemetry payloads, configuration frames, or command streams across the serial communication line. Ingress Interface: The physical UART controller receives the serial data stream and buffers incoming bytes into its internal receive holding registers accessible via the UART’s AXI4-Lite control interface. Transport Mechanism: The VeeR EL2 core retrieves received data from the UART controller through memory-mapped register accesses over the AXI4 interconnect via the UART’s AXI4-Lite slave interface. Initial Storage Destination: The core then issues write transactions through its AXI4 LSU master interface across the 64-bit interconnect to deposit the telemetry bytes directly into the System SRAM staging buffer, establishing the base payload for subsequent processing branches. 5.3 SRAM as the Data Buffer Buffer Role: The System SRAM serves as the primary on-chip staging area and memory-mapped repository where raw telemetry payloads, intermediate processing blocks, and final encrypted outputs reside. Interface Access: Both the VeeR EL2 core via its LSU interface and the DMA controller access the SRAM as central memory slaves over the 64-bit AMBA AXI4 interconnect. Functional Purpose: It decouples the ingress and egress routines from high-speed cryptographic and transfer operations by providing stable, addressable memory ranges. Operational Boundary: The SRAM provides addressable storage for telemetry payloads, intermediate data, and encrypted results accessed through the AXI4 interconnect. 5.4 DMA Data Movement Transfer Source: The DMA controller reads payload data from configured base addresses residing within the System SRAM. Transport Mechanism: Operating as an independent AXI4 master on the system interconnect, the DMA controller executes block data transfers without requiring byte-by-byte CPU intervention. Execution Processing: The DMA controller operates using transfer parameters configured through its control interface and manages the programmed data movement autonomously while signaling completion or error states via separate interrupt lines to the PIC. Transfer Destinations: Supported architectural transfers map explicitly to the hardware endpoints: System SRAM to SHA-256 accelerator data interface for integrity verification. System SRAM to AES-256 CBC engine data interface for block cipher transformation. AES-256 CBC engine to System SRAM for writing back finalized ciphertext results. 5.5 SHA-256 Data Path Data Source: Buffered plaintext telemetry blocks residing in System SRAM. Transport Mechanism: The DMA controller streams these blocks across the AXI4 interconnect directly into the SHA-256 accelerator data interface. Processing Operation: The hardware accelerator computes the cryptographic message digest entirely through dedicated internal logic without modifying the underlying data blocks. Result Destination: The resulting 256-bit hash digest is held in internal accelerator result registers, from which it is retrieved by the processor through the accelerator's control interface. 5.6 AES-256 Data Path Data Source: Plaintext telemetry payload blocks stored within System SRAM. Transport Mechanism: The DMA controller reads and streams the plaintext blocks over the AXI4 interconnect into the AES-256 CBC engine data interface. Processing Operation: Operating in Cipher Block Chaining mode, the engine combines incoming plaintext blocks with an Initialization Vector (IV) and a pre-loaded 256-bit key, chaining ciphertext dependencies across sequential transformation cycles. Result Destination: The resulting encrypted ciphertext blocks are written back across the AXI4 interconnect and stored in a designated result buffer within System SRAM. 5.7 Data Egress Egress Source: Finalized, encrypted payload blocks residing within the System SRAM result buffers. Transport Mechanism: Under firmware direction, the VeeR EL2 core reads the secured payload from SRAM using its AXI4 LSU interface and directs it toward the UART control registers via the AXI4 interconnect through the UART’s AXI4-Lite slave interface. Processing Operation: The UART controller accepts the bytes through AXI4-Lite register writes and serializes the data stream according to pre-configured baud rates and frame formats. External Destination: The serialized ciphertext leaves the SoC pins across the serial communication line to reach the external host or ground station.
